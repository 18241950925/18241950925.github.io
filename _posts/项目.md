### 主项目一：DeepSeek MoE Gate/Up Q4 权重布局优化

#### 一句话版本

> 通过 profiling 发现 Q4 MoE Gate/Up 热路径包含 host repack、DSP Q4 decode 和 HMX FP16 tile transform；在排除 loop reorder 后，我把权重提前打包成 HMX-friendly 的 x4 K-tile 布局，以离线空间和兼容分支换取更少的运行时转换，使局部 Gate/Up 降低 41.6%、pp1024 端到端 prefill 提升 10.67%，并保持 PPL 一致。

#### 问题与诊断

- MoE 每层只激活部分 expert，但命中的 expert 权重仍需进入 Gate/Up fused matmul 路径。
- 原路径为：`Q4_0 原始布局 → host repack → DSP 解码 → HMX FP16 tile-major 转换 → HMX matmul`。
- profile 显示 dequant/layout transform 是 Gate/Up 的主要热区，因此问题不仅是矩阵乘本身，而是“为了让矩阵单元吃到合适布局，运行时付出了多少准备成本”。
- 曾假设通过交换 M/N 循环顺序复用权重；但路由统计显示单 expert 的 `m_chunks` 基本为 1，没有足够的 M 维复用，重排还增加 activation gather，因此用数据否定该方案。

#### 优化设计

- 将重复且与输入无关的布局工作前移到 host/离线阶段，直接生成 HMX 需要的 packed Q4 tile。
- fast path 一次处理连续 4 个 K tile，降低循环、地址计算和重复转换开销，并保留批处理优势。
- 保留默认兼容路径，用环境变量选择实验路径，便于做严格 A/B、快速回退和控制正确性风险。
- 本质是用更多的离线准备、存储布局约束和实现复杂度，换取热路径更低的 dequant/repack 成本。

#### 为什么这属于算子/编译优化问题

- **数据布局决定可生成的高效代码**：逻辑上相同的权重，物理排列不同，会改变连续访存、向量 load、tile 填充和矩阵单元喂数效率。
- **把运行时不变量前移**：权重布局只依赖模型参数和目标硬件，可视为 ahead-of-time packing；这和编译器的 constant folding、layout propagation、weight prepacking 思路一致。
- **需要合法性与收益判断**：只有 dtype、shape、对齐和硬件路径满足条件才进入 fast path，否则回退；工程上相当于带 guard 的 specialization。
- **局部提速不等于端到端提速**：必须继续检查 attention、路由、其他 expert、CPU 提交等剩余瓶颈。

#### 指标与验证

- pp1024：`641.06 ± 17.98 t/s → 709.46 ± 17.30 t/s`，端到端提升 **10.67%**。
- Gate/Up：`12335 μs → 7200 μs`，降低 **41.6%（1.71x）**。
- Dequant：`8461 μs → 3225 μs`，降低 **61.9%（2.62x）**。
- 正确性：PPL 保持一致；默认路径不受影响。

#### 高频追问

**Q：为什么不直接优化 HMX matmul？**

A：profile 指向的主要开销是进入 matmul 前的解量化和布局转换。如果矩阵单元没被持续喂饱，单独提高 matmul 峰值不会等比例改善端到端。应先优化占比最大且可以消除的准备工作，再用新 profile 判断下一瓶颈。

**Q：为什么 x4 K-tile 会更快？**

A：核心不是数字 4 本身，而是批量处理相邻 K tile 后，可以摊薄循环控制、索引计算和转换开销，并形成更连续的 load/store。最终是否有效取决于 tile 尺寸、向量宽度、对齐、VTCM/寄存器压力和真实 shape，需要 benchmark 而不能只凭直觉。

**Q：预打包的代价是什么？**

A：会增加模型准备时间、格式维护成本，可能带来 padding 或额外存储，也会使格式与特定硬件耦合；动态权重或 shape 不满足 guard 时收益有限。因此要保留通用路径，并把格式版本、对齐条件和兼容性纳入设计。

**Q：如果迁移到国产训练卡，思路如何复用？**

A：先确认矩阵单元支持的 dtype、tile 和 layout，再检查框架图中是否反复出现 transpose/cast/reformat。对静态参数可做离线 prepack，对 activation 则通过 layout propagation、算子融合或 producer-consumer 协同减少转换。训练场景还要处理权重更新：master weight 和 optimizer state 会变化，不能简单永久预打包，需要在参数更新后重排、使用硬件原生布局保存参数，或把布局转换融合进优化器。

### 主项目二：HMX Flash Attention mask 正确性修复

#### 一句话版本

> HMX 路径把所有小于 `-16` 的 FP16 mask 值都当成不可见位置，误删了合法的有限负 attention bias；我通过关闭 HMX 的参考路径和 focused test 将问题定位到 mask 语义，修改为仅屏蔽真正的 FP16 `-inf`，使 focused test 从 12/56 提升到 56/56、完整回归达到 2176/2176，并恢复真实模型生成。

#### 必须讲清的数学语义

Attention 的核心是：

`S = QK^T / sqrt(d) + mask_or_bias`

`P_i = exp(S_i - max(S)) / Σ_j exp(S_j - max(S))`

有限负 bias 表示“降低该位置概率”，它仍应进入 softmax；`-inf` 才表示该位置概率严格为 0。用固定阈值把小于 `-16` 的数全部丢弃，会把连续的 bias 语义错误地变成布尔 mask 语义，改变输出分布。

#### 定位路径

1. 相同输入下，关闭 HMX 全通过、开启 HMX 大量失败，先把范围缩到 HMX fast path。
2. focused case 的最大误差接近 `0.98`，不像普通 FP16 累积误差，更像分支或语义错误。
3. 对比 mask/bias 处理，发现阈值判断错误地屏蔽有限负值。
4. 修复后依次做 focused test、完整算子回归、真实 OLMoE 生成，避免只在单一 fixture 上过拟合。

#### 指标与验证

- focused test：`12/56 → 56/56`。
- 完整 `FLASH_ATTN_EXT`：`2176/2176`，`FAIL=0`。
- 真实生成恢复正常；开启 Flash Attention 后 prompt 吞吐 `64.6 → 71.2 t/s`。

#### 高频追问

**Q：为什么 softmax 要减去最大值？**

A：不改变最终概率，因为分子分母同时除以 `exp(max)`；但能防止大正数 `exp` 上溢。低精度下还要关注累加精度、online softmax 的 running max/running sum 更新和全 mask 行等边界情况。

**Q：如何区分算法误差和实现 bug？**

A：先用可靠路径做 reference，固定输入比较逐元素误差；再看误差量级、分布和出现条件。微小且随归约长度增长的偏差更像舍入/累积误差，接近 1 的结构性偏差更像索引、mask、layout 或同步问题。随后用最小 shape、特殊 mask、全 mask/无 mask/有限 bias 等用例缩小范围。

**Q：为什么不能为了性能近似处理 mask？**

A：近似必须符合上层算子的契约，并有明确误差界和调用方约束。这里输入允许有限负 bias，因此阈值化改变了语义，不能作为合法近似。若专门为纯 causal boolean mask 写 fast path，应通过 dtype/模式 guard 区分。

### 主项目三：GPT-OSS MoE dispatch 粒度与 capacity 优化

#### 一句话版本

> profile 显示 NPU 时间占比很高，但 HMX 平均利用率只有 1.3%、HVX 18.4%，Q6 控制核却满频，说明瓶颈主要是权重搬运、频繁 graph dispatch 和 slot 利用率，而不是矩阵峰值算力；我保持 attention chunk=128 以控制内存，同时把 MoE dispatch 合并到 512 token 并配套扩大 expert capacity，使 graph call 从 384 降到 96、pp2048 prefill 提升 10.3%。

#### Roofline 判断

- 算术强度 `AI = FLOPs / bytes moved`。
- 可达到的性能上界 `P ≤ min(P_peak, AI × BW)`。
- 该场景估算 AI 约 `248 FLOPs/byte`，低于 HTP Roofline 拐点约 `800 FLOPs/byte`，优先判断为 memory/dispatch-bound，而非 compute-bound。
- Roofline 是方向判断，不是最终证据；还需结合 HMX/HVX/Q6 利用率、DMA、graph call、CPU fallback 和 timeline。

#### 为什么解耦 attention 与 MoE chunk

- attention 和 MoE 的资源约束不同，不应机械共用同一 chunk。
- attention 增大 chunk 会增加中间状态和 CDSP 内存压力，因此保持 128。
- MoE 合并到 512 token 后，一次 dispatch 可聚合更多路由 token，提高单次 expert 权重复用并摊薄提交/调度成本。
- capacity 决定每个 expert graph 可容纳的 token 数；只增 dispatch 不增 capacity 会产生 overflow 或 CPU fallback，因此两者需要协同调整。

#### 指标与代价

- NPU graph calls：`384 → 96`，减少 **4 倍**。
- NPU expert 执行：`17.65 s → 13.80 s`，提升 **1.28x**。
- pp2048：`89.9 → 99.2 tok/s`，端到端提升 **10.3%**。
- 代价是更大的 expert context/capacity、可能增加内存占用和排队时延；最优 chunk 会随模型、序列长度、路由分布和设备内存变化。

#### 高频追问

**Q：NPU busy 很高，为什么利用率仍然低？**

A：busy 只表示设备在处理任务，不表示矩阵单元持续做有效 MAC。控制核调度、DMA 等待、layout 转换、小 shape、同步和 fallback 都可能计入时间。必须把设备占用和具体执行单元利用率分开看。

**Q：为什么 graph call 减少 4 倍，端到端只提升 10.3%？**

A：优化只覆盖 MoE expert 子阶段，端到端还包含 attention、路由、host 提交、数据搬运和其他固定开销；同时更大 dispatch 也可能引入 padding、capacity 和内存成本。Amdahl 定律决定局部收益会被未优化部分稀释。

**Q：chunk 是否越大越好？**

A：不是。增大 chunk 可以摊薄 launch/dispatch、提高权重复用，但会增加工作区、padding、排队时延和片上存储压力，甚至触发 OOM。需要在固定场景下 sweep，并同时观察 TPS、峰值内存和 p95/p99 时延。

### 备选项目四：NPU Prefill + CPU Decode 异构路径

#### 核心逻辑

- Prefill 有较大的 token 维度并行度，NPU 更容易发挥吞吐；decode 通常每步一个或少量 token，更容易受 launch、状态和权重搬运影响。
- 在 NPU 完成 prefill 后，将有效范围内的 KV cache 复制到 CPU context，然后释放 NPU prefill context/model，再进行 CPU prewarm 和 decode。
- 关键正确性约束包括层数、K/V 张量布局、token range、position、dtype、stride 和 context 元数据一致。
- 释放 NPU context/model 后，decode 从 `1.80 t/s` 恢复到 `20.64 t/s`；CPU prewarm 将 pp2048+tg2048 中 `>300 ms` token 次数从 50 降到 0，端到端 `15.67 → 17.21 t/s`。

#### 追问准备

- 为什么 NPU 资源常驻会拖慢 CPU：从共享内存带宽、功耗/频率预算、缓存压力、线程/驱动资源竞争提出假设，并明确最终结论应以实验和 trace 为准。
- KV cache 大小估算：传统 MHA 近似为 `2 × L × B × S × H_kv × D_head × bytes`；GQA/MQA 中使用 KV head 数而不是 Q head 数。
- 拷贝何时值得：比较 NPU prefill 节省的时间、KV copy 与 context 切换成本、预计 decode 长度和 CPU/NPU decode 速度。

### 备选项目五：跨层 MoE Expert 预测预取

#### 核心逻辑

- 当前层 hidden state 与下一层 router top-K 存在统计相关性，可在当前层计算期间预测并 staging 下一层候选 expert 权重。
- top-K 太小会 miss，太大会造成无效搬运和内存占用；因此需要联合评估 offline recall、候选精度、加载字节数和在线 `tg1` 吞吐。
- top-6 配置将单 token decode 从 `0.705 t/s` 提升到 `1.345 t/s`，提升 **90.8%**。
- 两阶段预测器的 Top-6 recall 为 `69.98%`，说明不需要 100% 命中也可能获得收益：只要命中的预取覆盖了关键路径的一部分，且错误预取代价受控即可。

#### 追问准备

- miss 时必须有正确的按需加载 fallback，预测只能影响性能，不能影响模型输出。
- 预取有效的条件：计算与 DMA 可重叠、存在足够提前量、带宽未饱和、额外候选不挤占关键数据。
- 训练卡上相似问题包括 MoE expert parallel 的 all-to-all、expert placement、token dispatch 和计算通信重叠；但端侧 expert staging 不等同于分布式 EP，回答时应区分。

### 项目统一回答框架

任何项目都按下面 6 步回答，避免只罗列“做了什么”：

1. **场景与约束**：模型、硬件、prefill/decode、dtype、内存或正确性要求。
2. **现象与基线**：哪个指标慢，基线如何复现，性能口径是什么。

#### 前端部分
1. 词法分析 (Lexical) 与语法分析 (Syntax)
流程：parser/lexer.c 和语法解析规则（Flex/Bison 生成）。将文本流转换为 Token 流，然后依靠语法规则生成抽象语法树（AST）。
数据结构：在你的项目里，这对应 common/syntax_tree.h 和 common/ast.hpp。ast.hpp 定义了各种树节点，比如 BinaryExpr（加减乘除）、IfStmt（条件分支）、WhileStmt（循环）等。
1. AST 遍历与环境状态维护 (Visitor Pattern + Scope)
生成 IR 的核心机制是访问者模式（Visitor Pattern）。

在 sysy_builder.hpp 中，应该有一个构建器（Builder）类继承自 AST 的 Visitor。它重载了 visit(IfStmt* )、visit(BinaryExpr* ) 等方法。
它需要维护一个符号表（Symbol Table），记录当前作用域内的变量名到其分配的内存地址或 Value* 的映射。这样遇到 a = b + 1 里面的 b 时，能知道去哪个地址 Load 数据。
3. IRBuilder 与指令的生成（最关键的一步）
项目目录中有一个极其重要的文件：IRBuilder.hpp。它的作用就像是一个在流水线上的“打字机”。

维护插入点（Insert Point）：IRBuilder 内部保存了当前正在操作的 BasicBlock（基本块）。当你调用 builder->create_add(v1, v2) 时，它会自动生成一条对应的加法 Instruction，并将其 push_back 到当前基本块的指令链表（ilist）末尾。
4. 具体控制流结构如何生成？ (If / While)
这是面试常考的重点！如果在 AST 层遇到一个 while(exp) { body }，你的 Builder 会怎么生成 LightIR 的图？

生成新的基本块：用 BasicBlock::create(...) 创建至少 3 个基本块：cond_block（条件块）、body_block（循环体块）、next_block（退出循环的块）。
连接跳转指令（Branch）：
在进入 while 之前，生成一条无条件跳转指令跳转到 cond_block。
让 IRBuilder 的插入点移动到 cond_block，遍历生成 exp （条件表达式）的 IR。
根据 exp 的结果（Value*），利用 IRBuilder 生成一条条件跳转指令（Br cond_val, body_block, next_block）。
处理循环体：
将插入点移动到 body_block，递归调用 Visitor 处理循环体内部的 AST 节点。
循环体末尾，插入无条件跳转，跳回 cond_block。
结束点：将插入点移动到 next_block，继续处理后续的 AST。

## mlir项目（fhe编译优化实现）
### 自举算子插入优化
基于动态规划算法优化自举算子的排布，性能相比传统手动插入提升20%。
- dp算法：这个 Pass 是我在基于 MLIR 构建的同态加密（HE）编译器中，为解决自举（Bootstrapping）操作最优插入问题而设计的核心优化模块。在同态加密计算中，自举操作耗时极高，同时长程数据依赖（Shortcuts）为了满足密文层级（Level）对齐的硬性要求，会强行压低沿途其余计算节点的可用层级，导致整体计算延迟剧增。为了最小化程序的端到端执行时间，我将该节点选址问题抽象为动态规划（DP）模型：用 DP 数组记录沿着计算图深度推进时，在每一层发生自举的最小累计延迟。在设计状态转移方程时，为了解决长程边带来的层级挤压矛盾，我引入了长程边子集枚举与代价评估策略，在‘保留长程边但牺牲同深度普通节点计算速度’与‘强制打断长程边增加单次自举开销以换取局部计算提速’之间进行精确的 Trade-off。最终，算法通过回溯 DP 路径，全局寻找到了自举开销与密集计算延迟之和最小的最优插入边界点与必须被阻断的长程边集合，并在 IR 层级为对应节点打上 Boot=true 标签，为后端代码生成提供了极具性能优势的自举调度策略。
> 算法详细拆解：
> 1. 明确 DP 状态定义与转移思路
“首先，我设定 DP 数组 dp[i] 来表示：当计算图推进到深度 i 并且恰好在第 i 层执行了一次自举操作时，整个程序端到端的最小累计延迟。
在计算 dp[i] 时，我们需要回头去寻找上一个最优的自举位置 j。那么状态转移方程的核心，就是如何精确计算在区间 [j, i] 之间不发生自举的期间，所产生的区间总延迟代价。”
>2. 解释引入难点：长程边（Shortcuts）与层级挤压矛盾
“计算区间代价时，最大的阻碍来自于跨越该区间的长程数据依赖（Shortcuts）。在同态加密的机制中，密文的每次乘法都会消耗可用的层级（Level），层级耗尽就必须做自举。
如果有一条长程边跨越了 [j, i] 这一长段区间，为了让这个数据能活着送达底层而不报错，在层级对齐机制下，它会强迫压低沿途经过的所有深度的可用层级。而同态加密中，节点在越低的层级下执行，耗时就越长。这就是所谓的‘层级挤压’导致普通节点变慢的问题。”
>3. 详细拆解 Trade-off（权衡决策）
“为了打破这个僵局，我们在处理每一条长程边时，其实都面临一个极端的 Trade-off：”
策略 A（保住长程边）：选择顺应长程边，不在起点 j 把它干掉。代价是：它会触发层级重新分配，拖慢区间内所有普通节点的计算速度。
策略 B（强制打断长程边）：选择在起点 j 强制让这条长程边也执行一次自举运算。代价是：承受一次巨大的固定自举延迟开销；收益是：消除了它对局部层级的束缚，区间内的普通节点可以分配到更高的层级，从而获得计算上的大幅提速。”
>4. 算法落地：子集枚举与精确代价评估
“由于现实计算图中，跨越某个区间的长程边往往不止一条，这是一个典型的组合优化子问题。因此我设计了长程边子集枚举机制：
对于当前评估的区间 [j, i]，我会先收集所有穿过它的长程边，然后枚举它们所有可能的保留组合（子集）。针对每一个子集，我都会进行一次模拟评估：
计算代价 = 『未能保留的长程边需要额外执行自举的开销总和』 + 『剩余节点在新的受限层级下的实际计算耗时总和』。
通过比较所有子集的结果，算法能动态地判断出：在当前的图结构和层深下，到底放弃哪些长程边、保留哪些长程边才是全局最划算的。最后取出这个最优子集的代价，作为 DP 状态转移的最优成本，从而彻底解决层级分配与开销最小化之间的矛盾。”

## cuda编程项目
针对 SNN 多时间步迭代导致访存密集的问题，独立设计并实现了一个基于 LeNet 架构的 CUDA SNN 前向推理引擎，支持 FashionMNIST 数据集的图像分类
### SNN介绍
与CNN不同，需要在时间维度上进行迭代，导致访存密集，性能较差，比如项目中需要循环8次

### GPU架构
GPU的核心是SM（Streaming Multiprocessor），每个SM包含多个CUDA核心，负责执行并行计算任务。
1. 逻辑结构：由grid，block和thread组成，线程是GPU执行的基本单位，线程块是线程的集合，网格是线程块的集合。
2. 内存层次：包括寄存器、共享内存、全局内存等，不同类型的内存具有不同的访问速度和范围。
3. 物理结构：GPU由多个SM组成，每个SM包含多个warp，每个warp中的（32个）线程同时执行相同的指令。
4. bank冲突：shared memory被划分为32个bank， 如果在$32 \times 32$ 的共享内存矩阵中，线程访问的地址在同一个bank中，就会发生bank冲突，导致性能下降。使用padding可以避免bank冲突。

### 项目细节
项目描述：使用 CUDA C++ 从头实现并优化了一个 SNN (脉冲神经网络) 的前向推理引擎，对 FashionMNIST 数据集进行分类。
网络架构：LeNet-5 变种 (Conv1 -> Pool1 -> Conv2 -> Pool2 -> FC1 -> FC2 -> FC3)。时间步长 T=8
核心优化点：
算子融合 (Kernel Fusion) / 持久化核函数 (Persistent Kernel)：没有调用 cuDNN 等库，而是直接手写了一个巨大的 persistent_infer_kernel，将所有的卷积、池化、全连接层以及 SNN 的时间循环 (T=8) 全部融合在一个 Kernel 中。避免了频繁的 Kernel launch 开销和中间变量在全局内存 (Global Memory) 中的反复读写。
细粒度并行映射：采用 Batch 并行策略，1 个 Block 处理 1 个样本 (blockIdx.x + batchOffset)。Block 内的 256 个 Threads 协同处理特征图和全连接层向量。
共享内存 (Shared Memory) 优化：使用 Shared Memory 协同加载整个输入图像 (28x28) 以及中间的 Pool1 结果。因为图像和特征图在卷积核滑动时会被重复读取，放进 Shared memory 极大降低了 Global Memory 带宽压力。
寄存器缓存与循环展开 (Register Caching & Unrolling)：在算子计算时，将小尺寸的卷积核窗口 (如 5x5 的 Conv1_K) 先手动提取入片上寄存器 (Register Array patch[CONV1_K * CONV1_K]) 再进行计算，配合 #pragma unroll 提升指令级并行度 (ILP)。
内联 PTX 汇编优化：通过手动编写内联汇编 ptx_fma_f32 强制发射 fma.rn.f32 (乘加融合指令)，最大化 ALU 计算吞吐量。
🤔 面试高频问题模拟 (Q&A)
1. 为什么采用一个大 Kernel (Persistent Kernel) 把所有层写在一起，而不是逐层 Launch Kernel？
回答要点：

消除 Launch Overhead：每次调用 Kernel 都有微秒级的开销。特别是在 SNN 中，计算包含一个时间循环 (T=8)，如果每层、每个时间步都 launch，相当于要几百次 launch，开销占比巨大。
数据局部性 (Data Locality)：融合在一块后，前一层的结果（或者说特征图甚至膜电位）可能还在 L1/L2 Cache 或者 Shared Memory 中，下一层直接读取处理，显著降低了昂贵的 Global Memory 访存开销。
1. 在这个 CUDA 程序里，你是如何使用 Shared Memory 优化的？
回答要点：

用途：主要用于缓存输入图像 (s_input) 和池化层1的输出 (s_pool1)。
原因：卷积操作具有极强的数据重用性 (Spatial Locality)。相邻的输出像素需要读取大面积重叠的输入像素。如果直接从 Global Memory 读，带宽会成为瓶颈。
实现：Block 启动后，首先让 256 个线程通过步进 (for (int i = tid; i < size; i += nthreads)) 协同搬运 Global Memory 的数据到 Shared Memory 中，然后调用 __syncthreads() 同步，最后各个计算线程都从 Shared memory 去取 patch 数据。
3. 你的 Block / Thread 并行划分策略是什么？有哪些利弊？
回答要点：

策略：采用 grid(bs), block(256)。即一个 Thread Block 负责计算 Batch 中的一张完整的图片，Block 内的 256 个 Thread 根据元素的全局索引 (idx = tid; idx < total; idx += nthreads) 分摊该层各个特征图/神经元的计算任务。
利 (优点)：易于共享该图片的中间数据（通过 Shared Memory 存中间特征图）。无需不同 Block 之间的同步，因为每个样本的推断是独立的。
弊 (潜在改进点)：256 个线程去平摊并行度，对于全连接层或较小特征图的情况可能导致资源利用不足。更大规模的网络可能需要 "把特征图拆分给多个 Block" 或者使用 Tensor Core。
4. 代码中看到了 ptx_fma_f32，为什么要手写 PTX 汇编指令？
回答要点：

FMA 表示 Fused Multiply-Add (d=a×b+c)。
在硬件底层，NVIDIA GPU 对乘加操作有专门的 FMA 指令执行单元。如果不加干预，编译器有时为了严格遵循浮点标准可能不会自动将乘法和加法折叠。
通过手动使用内联汇编强制发射 fma.rn.f32 指令，可以确保这两个运算在一个时钟周期内完成（并且只舍入一次提高精度），从而把计算逻辑的吞吐量压榨到极限。该手段常用于卷积、矩阵乘这类典型的计算密集型算子。
1. SNN (脉冲神经网络) 的计算和传统 CNN 在这段代码里的体现有什么区别？
回答要点：

网络增加了时间维度 for (int t = 0; t < T; ++t)。
增加了在时间维度上持久存在的膜电位 (Membrane Potential) 数组（如 d_conv1_pot）。
激活函数由 ReLU 变成了 LIF (Leaky Integrate-and-Fire) 模型的核心逻辑：即电压 V 累加输入后，判断 if (V > threshold)，如果超过阈值发出脉冲 (返回 1.0f 或者 boolean)，并将电压重置。脉冲(spike)会被作为下一层的输入传递。
