## 二、核心成果

### 1. 修复 HMX Flash Attention 数值精度问题，恢复端侧生成正确性

**问题背景**

在 Hexagon HMX Flash Attention 路径上，开启 HMX 后大量 `FLASH_ATTN_EXT` 算子测试失败，误差接近 `0.98`；关闭 HMX 时相同测试全部通过。问题会进一步影响真实模型生成质量，属于“性能路径可跑但数值不正确”的高优先级缺陷。

**我的工作**

- 将问题定位到 HMX Flash Attention 中的 mask 判定逻辑。
- 分析发现旧实现将所有小于 `-16.0` 的 FP16 mask 都视为不可见位置；这会错误丢弃合法的有限负 attention bias，改变 softmax 分布。
- 修改判定语义：仅将真正的 FP16 `-inf` 视为 mask，保留有限负值参与 `score + mask` 计算。
- 在 `ggml/src/ggml-hexagon/htp/hmx-flash-attn-ops.c` 完成修复，并完成算子级和真实模型两层验证。

**结果与价值**

- focused HMX Flash Attention 测试由 `12/56` 通过提升为 `56/56` 通过。
- 完整 `FLASH_ATTN_EXT` 测试达到 `2176/2176` 通过、`FAIL=0`。
- 在 OLMoE 真实生成任务中，开启 Flash Attention 后输出恢复正常；prompt 吞吐从 `64.6 t/s` 提升至 `71.2 t/s`。
- 建立了“先语义正确、再追求性能”的优化准则，避免将错误的快速路径当作有效优化。

**可用于简历的表述**

> 定位并修复 `llama.cpp` Hexagon HMX Flash Attention 的 mask 语义缺陷：将阈值式屏蔽改为仅屏蔽 FP16 `-inf`，使完整 `FLASH_ATTN_EXT` 回归测试 `2176/2176` 通过，并恢复端侧真实模型生成正确性。

### 2. 优化 DeepSeek MoE Gate/Up 权重解量化与布局转换，端到端 prefill 提升 10.67%

**问题背景**

DeepSeek MoE 16B 的 Q4_0 Gate/Up fused 路径中，权重会经历 host repack、DSP 端 Q4 decode、转换为 HMX FP16 tile-major layout、再执行 HMX matmul。profiling 表明，权重解量化和布局变换是关键热路径之一。

**我的工作**

- 对 MoE routing、active expert token 分布和 dequant 调用次数进行统计，验证实际瓶颈来源。
- 排除“仅调整 M/N loop order 即可减少 dequant”的错误方向：单 expert 的 `m_chunks` 基本均为 1，重排循环无法复用权重，反而增加 activation gather 开销。
- 将优化重心转向**改变权重初始布局**：在 host 侧直接生成 HMX-friendly packed Q4 tile。
- 设计并实现 packed x4 K-tile fast path，一次处理 4 个 K tile，同时保留原有批处理优势。
- 保持默认路径兼容，通过环境变量选择性启用实验优化，避免影响未启用优化时的原有行为。

**结果与价值**

- DeepSeek MoE pp1024 prefill 吞吐从 `641.06 ± 17.98 t/s` 提升至 `709.46 ± 17.30 t/s`，端到端提升 **10.67%**。
- Gate/Up 局部平均耗时从 `12335 μs` 降至 `7200 μs`，降低约 **41.6%（1.71x）**。
- Dequant 平均耗时从 `8461 μs` 降至 `3225 μs`，降低约 **61.9%（2.62x）**。
- 在保持 PPL 一致的前提下验证性能收益，形成“通过权重布局减少运行时变换”的可复用优化思路。

**可用于简历的表述**

> 面向 DeepSeek MoE 的 Hexagon HTP 后端设计 HMX-friendly Q4 packed x4 K-tile 权重布局，消除热路径中的部分解量化/布局转换；在 PPL 一致前提下将 pp1024 prefill 提升 `10.67%`，Gate/Up 局部耗时降低 `41.6%`。

### 3. 实现 NPU Prefill + CPU Decode 异构推理路径，解决长 decode 抖动

**问题背景**

NPU 对 prefill 的吞吐优势显著，但 decode 阶段在部分模型和序列长度下受限于小 batch、上下文状态和后端调度。目标是让 NPU 承担高吞吐 prefill，同时使用 CPU 稳定执行 decode，并正确迁移 KV cache。

**我的工作**

- 在 OLMoE fused Q4_0 上打通 NPU prefill 与 CPU decode 的异构执行路径。
- 实现并验证 KV range copy：将 NPU prefill context 中的 KV cache 迁移到 CPU decode context。
- 通过单一环境变量统一启用 CPU decode context、KV copy 与 NPU context 释放逻辑，降低实验和使用复杂度。
- 定位到 NPU prefill context/model 常驻会显著拖慢 CPU decode；在 decode 前释放 NPU context/model。
- 为 CPU decode 增加 prewarm，消除长 decode 中段的抖动。

**结果与价值**

- `pp1024 + tg128` 场景中，释放 NPU context 后 decode 速度从 `1.80 t/s` 恢复至 `20.64 t/s`。
- `pp2048 + tg2048` 场景中，CPU decode prewarm 将单 token 耗时超过 `300 ms` 的次数从 `50` 降至 `0`。
- 同场景端到端吞吐从 `15.67 t/s` 提升至 `17.21 t/s`，同时显著改善时延稳定性。
- 输出了一套清晰的异构生命周期设计：NPU prefill → KV copy → 释放 NPU prefill 资源 → CPU prewarm → CPU decode。

**可用于简历的表述**

> 在 OLMoE 端侧推理中实现 NPU Prefill + CPU Decode 异构路径，完成 KV cache 跨 context 迁移、NPU 资源释放和 CPU prewarm；在长生成场景将端到端吞吐从 `15.67` 提升至 `17.21 t/s`，并消除 `>300 ms` token 延迟抖动。

### 4. 实现 Qwen3-30B-A3B 跨层 Expert 预取，单 token decode 最高提升 90.8%

**问题背景**

对于端侧大规模 MoE，decode 阶段通常需要按 router 结果加载命中的 expert 权重；当权重加载和 staging 成为关键等待项时，可利用当前层 hidden state 预测下一层路由结果，提前搬运候选 expert。

**我的工作**

- 设计 decode-only 的跨层 expert 预取方案，预测关系为当前层 `ffn_inp` 到下一层 router top-K。
- 构建 rank-16、47 个预测槽位的 expert predictor，并定义 MPEP v2 二进制格式及端侧加载路径。
- 在 Android / 4×HTP session 环境中接入预测、候选 top-K 选择和 selected-expert staging。
- 扫描预取 top-K，平衡预测命中率、额外加载成本和实际 decode 吞吐；确定 top-6 为较优端侧配置。
- 进一步探索两阶段预测：P0 负责提前候选，Ptail 基于 post-MoE residual 补充候选；以条件化 KL 蒸馏训练预测器并进行跨数据集评估。

**结果与价值**

- 正常设备状态下，`tg1` decode 吞吐从 baseline `0.705 t/s` 提升至 top-6 的 `1.345 t/s`，提升 **90.8%**。
- 两阶段 residual-SiLU 预测器在 Wikitext-103 上达到 Top-6 recall `69.98%`、Top-8 recall `85.10%`；Top-6 候选精度约 `93.31%`。
- 验证了预测预取对端侧 MoE decode 的系统价值，并形成“预测准确度—预取数量—带宽/内存开销—吞吐”联合调优方法。

**可用于简历的表述**

> 设计并接入 Qwen3-30B-A3B 跨层 MoE expert 预测预取机制（MPEP 格式、端侧 top-K staging），在 Snapdragon HTP 的单 token decode 中将吞吐提升 `90.8%`；另行训练两阶段残差预测器，离线 Top-6 expert recall 达 `69.98%`。

### 5. 优化 GPT-OSS NPU MoE dispatch 粒度与 capacity，prefill 提升 10.3%

**问题背景**

GPT-OSS 20B MoE 的 NPU expert 执行存在明显的低利用率：NPU 时间占比很高，但 HMX/HVX 计算单元利用率低。原始设计中 attention 和 MoE 均以 128 token chunk 执行，导致 expert graph 调用频繁、单次权重复用不足。

**我的工作**

- 通过 sysfs 硬件利用率采样、profile JSON 和 trace 分析，建立 NPU 计算、调度和数据搬运的联合观测。
- 识别出“HTP 执行时间长”并不等同于“矩阵核计算饱和”：prefill 阶段 HMX 平均利用率仅 `1.3%`、HVX 平均利用率 `18.4%`，而 Q6 控制核满频。
- 将 attention chunk 保持为 128，避免 CDSP 内存问题；为 MoE 引入独立的 dispatch chunk，合并为 512 token 一次 dispatch。
- 配合 4× capacity 的 expert context 重编，降低 overflow 到 CPU 的比例，减少 NPU graph call 和 Q6 调度开销。

**结果与价值**

- NPU graph calls 从 `384` 降至 `96`，减少 **4 倍**。
- NPU expert 执行时间从 `17.65 s` 降至 `13.80 s`，提升 **1.28x**。
- pp2048 prefill 吞吐从 `89.9 tok/s` 提升至 `99.2 tok/s`，端到端提升 **10.3%**。
- 建立了“attention 与 MoE 可使用不同 chunk 粒度”的设计，并通过硬件利用率数据证明优化方向，而非只凭总耗时猜测。

**可用于简历的表述**

> 针对 GPT-OSS 20B NPU MoE 的低利用率问题，基于 HMX/HVX/Q6 利用率与 trace 分析解耦 attention 和 MoE dispatch chunk；通过 dispatch512 + 4× capacity 使 NPU graph 调用减少 4 倍、expert 执行提速 `1.28x`、prefill 吞吐提升 `10.3%`。

## 三、重要技术诊断与研究沉淀

以下内容更适合用于面试中展示分析能力，通常不建议占用简历的核心项目篇幅。

### 1. GPT-OSS NPU MoE 瓶颈定位

- 通过硬件利用率采样发现，NPU prefill 虽然耗时占比高，但 HMX 利用率低、HVX 利用率不足，实际瓶颈集中在权重搬运、Q6 调度和 slot 利用率。
- 量化分析表明，MoE 的 arithmetic intensity 为 `248 FLOPS/byte`，低于 HTP Roofline 拐点约 `800 FLOPS/byte`，属于 memory-bound 场景。
- 给出扩展 dispatch、提升 slot 利用率、合并 expert groups、减少中间搬运和探索 HMX 覆盖的优先级方案。

### 2. 端侧权重加载与内存机制梳理

- 分析 `llama.cpp` GGUF loader、mmap/mlock、CPU/HTP buffer placement、HTP rpcmem/FastRPC 映射和 KV cache 独立分配机制。
- 明确 mmap 只解决 CPU 文件映射及部分 zero-copy，不能等价为 HTP 权重按需流式加载。
- 将模型权重、KV cache、compute buffer、HTP submit 中的映射 buffer 统一纳入内存压力分析，为 MoE expert flash staging、rolling load 和 HTPPack 优化提供系统背景。

### 3. GPT-OSS Expert 的 W4A8 + LPBQ PTQ 离线校准流程

- 梳理并验证 Expert NPU 的 PTQ 流程：权重量化参数冻结、activation 统计、fake quant 开关、scale/zero-point 刷新、concat observer 一致性检查和部署格式转换。
- 理解 W4A8、LPBQ 二级 scale、QDQ 节点和 QNN AOT 图之间的关系，为容量扩展和 context 重编提供量化链路基础。

### 4. 面向端侧 MoE 的动态量化与权重驻留调研

- 基于 PagedWeight 研究，提出端侧可落地的分阶段路线：routing telemetry → 静态 per-expert 混合量化 → 热 expert 常驻 → KV-aware residency → 异步预取 → 动态多精度。
- 明确端侧场景不能只看平均 TPS；还应关注内存 headroom、cache miss、p95/p99 token latency 和权重迁移带来的抖动。

## 四、技术路线和方法论总结

### 1. 先建立正确的性能归因，再写优化代码

本次工作中多次验证：总 TPS、NPU busy 时间或单个 profile 指标都不能直接说明瓶颈。可靠的路径是：

1. 固定模型、输入、设备和运行参数，建立可重复基线。
2. 使用最终 benchmark 量端到端收益。
3. 使用 stage profile 观察大阶段变化。
4. 继续下钻到 HTP op、DMA、Q6/HVX/HMX 利用率、路由统计和内存行为。
5. 在算子测试、PPL/logits 或真实生成均通过后，再接受性能结论。

### 2. 对端侧 MoE，数据布局与调度往往比局部算子微调更关键

- Q4 权重的初始布局会决定是否产生额外 repack、dequant 和 tile transform。
- 低 batch 或稀疏路由下，expert 的权重复用、dispatch 粒度和 graph call 数常常比单个 matmul 峰值更重要。
- decode 阶段受单 token 工作形状限制，适合通过预测预取、异构调度、算子融合或连续 batching 改变系统工作形态。

### 3. 正确性是端侧推理优化的第一约束

- Flash Attention 的案例表明，错误 mask 语义也可能得到“看起来不错”的性能数据，但不能视为有效结果。
- 对性能敏感路径必须同步验证算子回归、数值误差、PPL/logits 和真实生成输出。
- 对异步执行系统，profile 各阶段可能存在重叠，不能简单相加后判断收益来源。

## 六、面试复盘提纲

### 1. 如果被问：“你最有代表性的优化是什么？”

建议优先讲 **DeepSeek MoE 权重布局优化**：

1. 问题：Q4 权重在运行时经历 repack、dequant 和 HMX tile transform，Gate/Up 热路径代价高。
2. 诊断：统计 expert token 与 dequant 调用，推翻单纯重排 loop order 的假设。
3. 方案：将 Q4 权重在 host 侧预先打包为 HMX-friendly x4 K-tile 格式。
4. 验证：默认路径不变、PPL 一致、局部 profile 和端到端 benchmark 同时改善。
5. 结果：Gate/Up 降 `41.6%`，端到端 prefill 提升 `10.67%`。

### 2. 如果被问：“性能提升如何保证没有牺牲正确性？”

建议用 **Flash Attention 修复** 回答：

- 先以关闭 HMX 的路径建立参考对照，确认问题仅出现在 HMX 实现。
- 通过 focused test 缩小范围，定位到有限负 mask 被误判为不可见位置。
- 修改后先跑算子级回归，再跑完整 `FLASH_ATTN_EXT` 测试，最后用真实模型生成验证。
- 结论是：性能路径必须满足相同数值语义；不能只因为 TPS 更高就接受优化。

### 3. 如果被问：“如何分析端侧 NPU 的瓶颈？”

可回答：

- 总耗时只能说明“慢”，不能说明“为什么慢”。
- 结合 profile JSON、Chrome Trace、sysfs 利用率和 routing/slot 统计，分别观察 HMX、HVX、Q6、DMA 与 CPU fallback。
- GPT-OSS 的案例中，NPU 占用高但 HMX/HVX 利用率低，说明问题是 memory/dispatch/slot utilization，而不是算力不足。
- 因而选择了扩大 MoE dispatch、减少 graph call 和提升权重复用，而非盲目改一个 matmul kernel。

### 4. 如果被问：“为什么 NPU prefill 后还要 CPU decode？”

可回答：

- prefill 是大 batch 计算，NPU 更容易发挥吞吐优势；decode 每步只有少量 token，系统调度与状态管理开销更突出。
- 通过 KV cache copy 将 prefill 结果转给 CPU decode context，再释放 NPU prefill 资源避免互相干扰。
- CPU prewarm 的作用是消除长 decode 中的频率、缓存或初始化抖动，优化目标不仅是均值吞吐，也包括 token 延迟稳定性。

### 5. 如果被问：“跨层 expert 预取为什么有效？”

可回答：

- MoE decode 中 expert 权重按 router 结果按需加载，加载与 staging 会进入关键路径。
- 当前层 hidden state 与下一层 router 有统计相关性，可预测候选 expert 并提前搬运。
- 关键不是追求 100% recall，而是控制候选 top-K：太小命中不足，太大会增加无效搬运和内存压力。
- 通过 offline recall、在线 `tg1` 吞吐、top-K sweep 三者共同选择配置。
